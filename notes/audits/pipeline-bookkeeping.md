# What the pipeline's own bookkeeping gets wrong

Audited 2026-08-18, against the question "is everything that feeds the final
climate correct and comprehensive?"

**The climate inputs themselves check out, and every piece of outstanding physics
is already tracked.** `rebuild_binaries.py --verify` reports sixteen resident
patches applied and all five binaries current; `check_consistency.py` is 30
checks with 0 failures and 2 warnings that explain themselves; `smoke_test.py` is
12 with 0 failures. Rule 1 holds in every consumer. The native mesh is present.
The cycle binary was rebuilt after the resident stack last moved and its pinned
base sha matches. `run_exoplasim.py` writes all four shortwave gas weights, with
`co2sww`'s default correctly taken as 0.0 rather than 1.0. The four runs on disk
carry no `h2osww` or `co2sww`, which is the no-op-until-enabled convention
working exactly as CLAUDE.md describes it.

So this audit is not about the physics, and it found nothing about the physics
that TASKS.md did not already carry. **It is about the machinery that is supposed
to tell you where the pipeline stands: the graph, the planner, the error budget
and the task file.** Four of those describe the pipeline incorrectly, and the
first one is why the pipeline cannot currently say when an iteration is finished.

---

## 1. The graph does not carry loop C at all, so nothing in it closes

`config/pipeline.yaml` declares four loops. Loop C is "the vegetation-climate
loop", with the exit predicate "re-take the verdict on modelled vegetation; if
basins flip, re-enter A".

**No step in the file carries `loop: C`.** Twenty carry A, four carry B, none
carry C or D.

The two edges that would close it are absent as well, and both are absent in the
same direction: the graph knows how to get INTO the biosphere and not how to come
back out.

- **Nothing declares `lpj_run` in its `needs`.** It is a leaf. The graph
  therefore says the biosphere is terminal, where `docs/src/pipeline/components.md` draws
  `fpc.out` returning to `build_surface_albedo.py --mode modelled` and `cpool.out`
  returning to `build_soil.py --soil-carbon`.
- **`surface_albedo` has `needs: []`.** Its `modelled` mode raises without
  `--vegetation <run>/fpc.out`, so in that mode it depends on `lpj_run`, and the
  graph records no dependency at all.
- **`soil` needs `[climatology, hydrography]`** and not `lpj_run`, so loop B's
  own feedback edge is missing too. Loop B's four steps are a chain, not a cycle.

Both flags exist in the scripts. `build_soil.py` documents `--soil-carbon <lpj
cpool.out>` in its module docstring; `build_surface_albedo.py` has `--mode
modelled` with `--vegetation` and a `SystemExit` if it is missing. So this is not
unbuilt capability. **It is built capability that the graph does not know about.**

**Why this is the finding that matters.** `docs/src/introduction.md`'s opening rule is that an
artifact no step generates does not exist, and that "what is now worthless" is
only answerable from a graph that is complete. The modelled-albedo field is
generated by no step. So:

- `pipeline.py --plan` cannot route to it, and `--status` cannot report it
  missing. Both are silent rather than wrong, which is the worse failure of the
  two the rule names.
- The carve gate is computed as "open tasks touching a step upstream of
  `carve_list`". With loop C outside the graph, no task can name a step in it, so
  no amount of outstanding vegetation work can ever register at the gate.
- Loop C's exit predicate is the only one of the four written as a re-taking of
  the verdict, and it is the predicate that decides whether an iteration is
  final. It is currently attached to nothing.

This is a graph completeness defect and not a plan change. The ordering already
exists in prose, in `docs/src/pipeline/sequencing.md` loop C, including the two checks that belong
there and why the flux moves by luminosity rather than by the orbit once the
calendar is locked. What is missing is the graph rows that make it computable.
Loop D is in the same state and is out of scope until A, B and C settle.

## 2. `pipeline.py --plan` cannot warn about the steps it exists to warn about

`cmd_plan` prints `[ check ]` and `continue`s for every step with
`presence: by_index`, and it does so before the line that increments `hours` and
before the line that prints the step's `gate`. Every step in the graph that costs
hours is `by_index`, because they are the model runs and runs are UUID-named.

- **The hour count is structurally always zero.** `--plan carve_list` today
  prints "21 steps in the closure, 0 of them cost hours" while three of those
  twenty-one are climate runs. The module docstring says the script exists
  because "five steps in the graph cost hours, and a script that could start one
  by accident is worse than no script", so the warning fails in exactly the case
  it was written for.
- **`stellar_cycle_run`'s gate can never print.** That gate is the one sentence
  in the graph saying a FINAL baseline is stricter than a converged one, and a
  planner will never be shown it.

## 3. The graph has one `climatology` step where the loop runs two

`climatology` writes fixed filenames and needs `assess_convergence`, which needs
`bootstrap_run`. The loop runs `build_climatology.py` twice, once per run, and
`docs/src/pipeline/sequencing.md` says to repoint `baseline_climatology` between them so
nothing downstream reads the bootstrap. There is no edge from `baseline_run` to
`climatology`, so `--plan carve_list` orders the climatology before the baseline
run and never schedules it again.

The closure is right, because `carve_verdict` reaches `baseline_run` through
`stellar_cycle_run`. The ORDER is wrong, and ordering is the half a planner is
for.

## 4. Two albedo deltas in the error budget are literals the albedo report contradicts

`scripts/error_budget.py` never reads
`exoplasim/inputs/t42/albedo_report.json`. Its `ALBEDO_ITEMS` are hardcoded, and
two have been overtaken:

| item | in the generator | in the current report |
| --- | --- | --- |
| lakes composited into albedo | -0.0139 | -0.02281, from `land_mean_albedo_before` 0.179066 to `after` 0.156256 |
| biosphere, bare rock vs vegetated | -(0.276 - 0.179) = -0.097 | `land_mean_bare_rock` is 0.24750, giving -0.0684 against the pre-lake vegetated mean or -0.0912 against the composited one |

The lakes item is understated by 64%. The biosphere item, which is the largest
row in the budget, is overstated by 6 to 30% depending on which vegetated mean is
the right comparand, and the report does not settle which. The generator's header
says the deltas are "the plausible RANGE of the item, not its current value",
which is why they are literals; for the lakes item the range IS the measured
delta, so that one is simply stale.

The same -0.0139 is quoted in prose twice in the workflow document, at sections 3.2 and
6, which the conventions forbid. `hydrography/notes/lake-solver-validation.md`
also carries it and keeps it correctly, being a dated record.

## 5. CLIM-13 measured: the bin weighting does not reach the carve verdict

CLIM-13 asks for an audit of what else quotes an annual mean of a strongly
seasonal field and names the carve criterion's evaporation as the one to check
first. Done here.

`carve_verdict.py:annual_mean` is `ds[name][:].mean(axis=0)`, an unweighted mean
over the twelve bins, and so are the Penman reference-level air state and the
seasonal rectification check.

**The bin weights this section first used were wrong, and are corrected here**,
measured 2026-08-18. They came from CLIM-13's original mechanism, 570 timesteps
for the first bin against 480 for the other eleven. That figure was a residual
derived by assuming eleven equal bins, so it forced every discrepancy onto the
twelfth; `TASKS.md` CLIM-13 carries the refutation. The real weights come from
pyburn's own binning, `np.linspace(0, ntimes, 13).astype(int)`, which at the
182 records per orbit of an `NLOWIO = 0` run gives

    [15, 15, 15, 15, 15, 16, 15, 15, 15, 15, 15, 16]

so two bins in twelve are under-weighted by 5.5% and the other ten
over-weighted by 1.1%. Bin 0 holds fifteen, the fewest. `lib/climatology.py`
derives this and checks it against the bin centres.

Recomputing the land-area-weighted means from `baseline_regular_climatology.nc`
with those weights:

| quantity | true vs equal weights |
| --- | ---: |
| land precipitation | +0.028% |
| land evaporation | -0.076% |
| land P - E, positive part | +0.162% |
| land wind speed | -0.025% |
| land `mrro` | +0.004% |
| global surface temperature | -0.001% |

Against the error budget's own basin response, where land precipitation +1% is
+39 basins, +0.028% is under +2 basins. That is inside every other term in the
budget and well inside the 769 basins the penman-to-wet bracket already disputes.

So **the verdict does not need re-taking for CLIM-13**, which removes it as a
reason to hold a carve.

a `[step: <id>]` marker records where work is filed, not what closing it would
change, and only the second bears on the gate. The finding stands and gets
sharper -- a stale status cell misleads a READER, and no traversal was ever
screening that out.)

## 7. Loose state worth settling before an expensive run

- **`exoplasim/patches/cycle_binary_manifest.json` is uncommitted.** It is the
  only record of which executable the cycle binary is, `check_consistency.py`
  reads it, and it was rewritten by the rebuild at 09:20:23Z.
- **`exoplasim/runs/run_67febcf213aa` is `status: prepared` and absent from
  `INDEX.json`.** Its `config_path` points into a scratchpad belonging to a
  different session, so the config it was built from is gone; its geography
  digest is ed88c1e3, matching the current inputs rather than the baseline's.
  Runs are untracked and `INDEX.json` is the only record of what each one was, so
  an unindexed prepared run is the state rule 6 exists to prevent. It looks like
  an abandoned attribution arm and should be started again rather than resumed.
- **Fourteen agent worktrees and their branches are still attached.** Gitignored
  and harmless to the pipeline, but `find . -name "*.md"` returns fourteen stale
  copies of every document in the repo, which is how an audit reads a superseded
  file believing it is current.

## What this audit did not find

Stated because the question asked was about the climate inputs and the answer is
a negative result, which is worth as much as a positive one.

Nothing was found wrong with the climate inputs, the boundary conditions, the
patch stack, the binaries or the provenance chain that the existing checks do not
already cover. Everything outstanding that moves the mean was already tracked
before this audit: PHYS-9, PHYS-10, SPEC-1, DUST-11, CLIM-11, CLIM-12 and CYC-1.
The state of the pipeline relative to a final climate is what those rows and
`docs/src/pipeline/sequencing.md`, A2 and A3 included, already says it is, and this document does not
restate them.
